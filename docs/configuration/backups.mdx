When you use a file-based storage backend, PerPlayerKit takes rolling snapshots of your data on its own so a corrupted database or a bad `/purgeitem` is never unrecoverable. Backups are enabled by default and run entirely off the main thread.

```yaml config.yml
backup:
  enabled: true
```

<ResponseField name="backup.enabled" type="boolean" default="true">
  Enables automatic backups for file-based storage. Set to `false` to turn the scheduler off entirely.
</ResponseField>

## What Gets Backed Up

Backups only cover **file-based storage** — the plugin cannot snapshot a database it does not own.

| Storage type            | Backed up | What to do instead                                                       |
| ----------------------- | --------- | ------------------------------------------------------------------------ |
| `sqlite`                | Yes       | —                                                                        |
| `yml`                   | Yes       | —                                                                        |
| `mysql` / `postgresql`  | No        | Use your database server's own backup tooling (`mysqldump`, `pg_dump`).  |
| `redis`                 | No        | Use Redis persistence (RDB snapshots or AOF).                            |

Each backup run copies the active storage file (`database.db` or `please-use-a-real-database.yml`) alongside a copy of `config.yml`, so a restore brings back the settings that data was written under.

## Schedule and Retention

Four independent timers run in parallel, each keeping snapshots for a different window. A cleanup pass runs every six hours and deletes anything past its retention period.

| Tier      | Runs every | Retained for | Filename prefix |
| --------- | ---------- | ------------ | --------------- |
| Hourly    | 1 hour     | 24 hours     | `hourly_`       |
| Daily     | 24 hours   | 7 days       | `daily_`        |
| Weekly    | 7 days     | 30 days      | `weekly_`       |
| Monthly   | 30 days    | 365 days     | `monthly_`      |

Timers start counting from server startup, so a server that restarts more often than once an hour never produces an hourly backup. Files land in:

```bash
plugins/PerPlayerKit/backups/
├── hourly_database_2026-08-21_14-00-00.db
├── hourly_config_2026-08-21_14-00-00.yml
├── daily_database_2026-08-20_09-00-00.db
└── ...
```

## Restoring a Backup

<Steps>
  <Step title="Stop the server">
    Never swap a storage file underneath a running server. Shut down completely first.
  </Step>

  <Step title="Copy the backup over the live file">
    Move the chosen snapshot out of `backups/` and rename it to the live filename — `database.db` for SQLite, or `please-use-a-real-database.yml` for YAML. Keep a copy of the current (broken) file first in case you need to compare.
  </Step>

  <Step title="Restore config.yml if needed">
    Each backup includes the `config.yml` from the same moment. Restore it too if the settings have drifted since.
  </Step>

  <Step title="Start the server and verify">
    Start up, check the console for storage errors, and confirm a test player's kits load as expected.
  </Step>
</Steps>

<Tip>
  Backups live inside the plugin folder, on the same disk as the data they protect. For anything you genuinely cannot lose, copy `plugins/PerPlayerKit/backups/` off the server on a schedule — or export a portable snapshot with [`/kitdata export all`](/guides/kit-data), which works on every storage backend.
</Tip>
