Most PerPlayerKit problems come down to one of five things: permissions, an empty kit room, the anti-exploit filter, storage configuration, or a version mismatch. Work through the matching section below.

## Startup and Loading

<AccordionGroup>
  <Accordion title="The plugin won't load at all" icon="triangle-exclamation">
    Check the console for the actual error, then verify:

    * **Server version** — Paper or Spigot **1.19 or newer**.
    * **Java version** — **17 or newer**. `java -version` on the host tells you what is actually running, which is not always what the panel claims.

    A plugin compiled for a newer Java than the server runs shows up as an `UnsupportedClassVersionError`.
  </Accordion>

  <Accordion title="Database errors on startup" icon="database">
    * If you do not specifically need a database server, set `storage.type: "sqlite"` — it needs no credentials and works out of the box.
    * For MySQL/PostgreSQL, confirm the database **already exists** (the plugin creates tables, not databases), the credentials are right, and the host is reachable from the server.
    * For remote databases, check the port is open: `3306` MySQL, `5432` PostgreSQL, `6379` Redis.
    * Connection-wait timeouts under load usually mean `maximumPoolSize` is too low.
  </Accordion>

  <Accordion title="/k10 and above don't exist" icon="layer-group">
    Slots above 9 only register when [`max-kits`](/configuration/kit-slots) is above 9, and only at startup. Raise the value and do a **full restart** — a reload will not register them.
  </Accordion>
</AccordionGroup>

## Permissions

<AccordionGroup>
  <Accordion title="Players can't use /kit" icon="key">
    They need `perplayerkit.use`, which bundles `perplayerkit.menu` and everything else a normal player uses.

    ```bash
    /lp group default permission set perplayerkit.use true
    ```
  </Accordion>

  <Accordion title="Admins can't build kits, only manage them" icon="user-shield">
    The tiers are **additive**. `perplayerkit.admin` grants admin commands only — it does not include the player-facing features. Give admin and staff groups `perplayerkit.use` as well.
  </Accordion>

  <Accordion title="Chat is full of kit messages" icon="volume-xmark">
    `perplayerkit.kitnotify` defaults to `true`, so everyone sees action broadcasts. Options, narrowest to broadest:

    * Deny `perplayerkit.kitnotify` for a group.
    * Disable individual actions under `messages` in `config.yml`.
    * Set `messages.disable-kit-messages: true` to silence all of them.

    See [Messages & broadcasts](/configuration/messages).
  </Accordion>
</AccordionGroup>

## Kits and the Kit Room

<AccordionGroup>
  <Accordion title="The kit room is empty" icon="warehouse">
    An admin has to stock it. Open `/kit`, click the **Nether Star**, fill each page, and **shift-right-click the barrier block** to save that page. Leaving without shift-right-clicking discards the page.

    Note that `/kitroom` on its own does not open the editor — it only takes `save` and `load`.
  </Accordion>

  <Accordion title="Items disappear from player kits" icon="ghost">
    This is the anti-exploit filter working as designed. With `only-allow-kitroom-items: true`, any item not present in the kit room is stripped from kits.

    * Add the missing item to the kit room, **or**
    * Set `only-allow-kitroom-items: false` to allow anything.

    Removing an item from the kit room retroactively affects saved kits that contain it. See [Anti-exploit](/configuration/anti-exploit).
  </Accordion>

  <Accordion title="A player's kits vanished after switching accounts" icon="user">
    Kits are keyed to a UUID, not a name. A name change keeps the kits; a different account is a different UUID. To move kits to a new account, use [`/transferkits`](/commands/sharing) from the old one while both are online.
  </Accordion>

  <Accordion title="Kits differ between servers on the same database" icon="server">
    Set the same [`max-kits`](/configuration/kit-slots) on every server sharing that database. A kit saved in slot 12 does not exist on a server capped at 9 slots.
  </Accordion>
</AccordionGroup>

## Features Not Working

<AccordionGroup>
  <Accordion title="Rekit-on-kill does nothing" icon="skull">
    Work down the list:

    1. `feature.rekit-on-kill.enabled` is `true`.
    2. The killer's world passes the whitelist/blacklist filter.
    3. The killer has `perplayerkit.rekitonkill`.
    4. If you configured a `kits` entry, the referenced **public kit id** exists and has contents saved with `/savepublickit`. Check the console for a warning.
    5. Region entries (`"world:region"`) require WorldGuard installed.
    6. You restarted after editing the config.

    See [Rekit on kill](/configuration/rekit-on-kill).
  </Accordion>

  <Accordion title="Regear restocks nothing" icon="arrows-rotate">
    * Regear pulls from the player's **currently loaded kit**. A player who has not loaded a kit this life has no source to restock from.
    * Only whitelisted items are restocked. Check the `whitelist` and `invert-whitelist` settings.
    * The `damage-timer` blocks regearing for a few seconds after taking damage, and `command-cooldown` limits repeat use.
  </Accordion>

  <Accordion title="A message still shows %player% or the wrong text" icon="message">
    Message text now lives in the [lang file](/configuration/languages), not `config.yml`, and placeholders use `{player}` rather than `%player%`. Edit `plugins/PerPlayerKit/lang/<code>.yml`.
  </Accordion>

  <Accordion title="Menu titles show raw tags like <blue>" icon="palette">
    That text is being read as literal rather than as [MiniMessage](/configuration/messages#minimessage-quick-reference). Check for an unclosed tag earlier in the same string, and escape any literal `<` as `\<`.
  </Accordion>
</AccordionGroup>

## Recovering Data

<AccordionGroup>
  <Accordion title="A purge or import removed something it shouldn't have" icon="clock-rotate-left">
    On SQLite or YAML, restore from `plugins/PerPlayerKit/backups/` — see [Backups](/configuration/backups). On MySQL, PostgreSQL, or Redis, restore from your database server's own backups, or from a `.ppk` snapshot if you took one.
  </Accordion>

  <Accordion title="Moving to a new database lost data" icon="right-left">
    Migration copies rather than moves, so the source is intact. Set `storage.type` back to the original backend and restart. Then re-run the migration, checking the console for the completion message before switching. See [Storage migration](/guides/storage-migration).
  </Accordion>
</AccordionGroup>
