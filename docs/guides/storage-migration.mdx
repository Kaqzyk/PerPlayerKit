If your server is growing and you need to move from the default SQLite database to MySQL, PostgreSQL, or Redis — or switch between any two supported backends — PerPlayerKit includes a migration command that copies all kit data across. The process is asynchronous, so the server stays online throughout. No third-party tools or manual SQL exports are required.

## Supported Backends

| Type         | Use Case                                          |
| ------------ | ------------------------------------------------- |
| `sqlite`     | Single-server setups; the default out of the box  |
| `mysql`      | Multi-server or larger deployments                |
| `postgresql` | Multi-server or larger deployments                |
| `redis`      | High-performance, distributed network setups      |
| `yml`        | Development and testing only — not for production |

## Migration Command

```bash
/perplayerkit migrate <source> <destination>
```

**Permission:** `perplayerkit.admin`. Works in game or from the console.

```bash
/perplayerkit migrate sqlite mysql
/perplayerkit migrate sqlite postgresql
/perplayerkit migrate mysql redis
/perplayerkit migrate redis sqlite
```

<Warning>
  Back up your data before migrating. For SQLite, copy `plugins/PerPlayerKit/database.db`; for YAML, copy `please-use-a-real-database.yml`. Automatic [backups](/configuration/backups) cover both, but a fresh manual copy is the fastest rollback.
</Warning>

## Step by Step

<Steps>
  <Step title="Back up your existing data">
    Copy your current database file somewhere safe. For a managed database, take a `mysqldump` or `pg_dump` snapshot.
  </Step>

  <Step title="Configure the destination in config.yml">
    Credentials must be in place **before** the migration runs — the plugin has to connect to the destination to write to it. Leave `storage.type` on the old backend for now.

    <Tabs>
      <Tab title="MySQL">
        ```yaml config.yml
        mysql:
          host: "localhost"
          port: "3306"
          dbname: "kitdatabase"
          username: "username"
          password: "pa55w0rd"
          useSSL: false
          maximumPoolSize: 10
        ```
      </Tab>

      <Tab title="PostgreSQL">
        ```yaml config.yml
        postgresql:
          host: "localhost"
          port: "5432"
          dbname: "kitdatabase"
          username: "username"
          password: "pa55w0rd"
          useSSL: false
          maximumPoolSize: 10
        ```
      </Tab>

      <Tab title="Redis">
        ```yaml config.yml
        redis:
          host: "localhost"
          port: 6379
          password: "pa55w0rd"
        ```
      </Tab>
    </Tabs>
  </Step>

  <Step title="Test connectivity">
    Confirm the database is running and reachable from the Minecraft server's host, and that the credentials work. Firewalls and closed ports are the most common blockers.
  </Step>

  <Step title="Run the migration">
    ```bash
    /perplayerkit migrate sqlite mysql
    ```

    Progress appears in chat and console, updating every 100 entries.
  </Step>

  <Step title="Wait for the completion message">
    Watch for **"Migration completed successfully!"**. Do not restart or change `storage.type` before it appears.
  </Step>

  <Step title="Switch storage.type">
    ```yaml config.yml
    storage:
      type: "mysql"
    ```
  </Step>

  <Step title="Restart the server">
    A full restart is required for the plugin to connect to the new backend.
  </Step>
</Steps>

## Post-Migration Checklist

Verify before announcing the change:

* [ ] No storage connection errors in the console at startup
* [ ] Kits load correctly for a test account
* [ ] Saving a kit works and survives a relog
* [ ] Public kits and the kit room are intact
* [ ] `max-kits` matches across every server sharing the new backend

## Troubleshooting

<AccordionGroup>
  <Accordion title="Connection error during migration" icon="plug-circle-xmark">
    The plugin could not reach the destination.

    * Recheck host, port, username, and password in `config.yml`.
    * Confirm the database process is running.
    * For a remote host, verify firewall rules allow the database port (`3306` MySQL, `5432` PostgreSQL, `6379` Redis).
    * If TLS is the suspect, set `useSSL: false` temporarily to isolate the problem.
  </Accordion>

  <Accordion title="Missing data after migration" icon="magnifying-glass">
    * Scroll back through the console for errors logged during the copy.
    * Confirm the success message appeared before you changed `storage.type`.
    * Confirm you saved `config.yml` and did a full restart rather than a reload.
  </Accordion>

  <Accordion title="Partial migration" icon="arrows-rotate">
    Run the same command again. Existing destination entries are overwritten and missed ones are filled in — re-running is safe.
  </Accordion>

  <Accordion title="Same source and destination" icon="ban">
    The command refuses a migration where source and destination are the same type. Pick two different backends.
  </Accordion>
</AccordionGroup>

## Rolling Back

The migration **copies** data; it never deletes from the source. To roll back, set `storage.type` in `config.yml` to the original backend and restart. Your original data is untouched.

<Tip>
  For very large datasets, migrate during a low-traffic window. The server stays online, but heavy kit activity during the copy can cause brief delays for players saving or loading.
</Tip>
