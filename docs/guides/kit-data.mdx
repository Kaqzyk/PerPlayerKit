`/kitdata` packages kit data into a single portable file so you can move a finished setup to another server — handing a polished kit room and public kit lineup to another owner, seeding a test server with real data, or keeping an off-site snapshot that does not depend on your storage backend.

**Permission:** `perplayerkit.admin`. Works in game and from the console.

## Exporting

```bash
/kitdata export <all|kitroom|publickits|playerkits> <file>
```

The file is written to `plugins/PerPlayerKit/<file>.ppk` — the extension is added for you.

```bash
/kitdata export all season4-backup
/kitdata export kitroom crystal-kitroom
/kitdata export publickits ffa-kits
```

<Note>
  If the target file already exists, the command stops and asks you to re-run it with `confirm` before it overwrites anything.
</Note>

### What Each Scope Contains

<AccordionGroup>
  <Accordion title="kitroom" icon="warehouse">
    The five kit room pages **as last saved to storage**.

    <Warning>
      Run `/kitroom save` first if you have edited the kit room since the last save. The export reads storage, not the live editor state.
    </Warning>
  </Accordion>

  <Accordion title="publickits" icon="globe">
    Every public kit **including its config entry** — display name and menu icon.

    On import, missing `publickits` entries are added to the receiving server's `config.yml` automatically and existing ones are updated, so the other server does not have to hand-edit its config. Kits declared in config but never saved with `/savepublickit` are carried over config-only.
  </Accordion>

  <Accordion title="playerkits" icon="users">
    All player kit and enderchest entries in the database.
  </Accordion>

  <Accordion title="all" icon="box-archive">
    Everything above in one file.
  </Accordion>
</AccordionGroup>

## Importing

Place the `.ppk` file in `plugins/PerPlayerKit/`, then:

```bash
/kitdata import season4-backup
```

If the import would overwrite existing data, the command first reports exactly what would be replaced — kit room pages, public kits, player kit and enderchest entries — and asks you to re-run with `confirm`.

```bash
/kitdata import season4-backup confirm
```

Caches refresh immediately afterward: the kit room, public kits, and the kits of affected online players are reloaded. No restart needed.

## How It Behaves

<Columns cols={2}>
  <Card title="Backend independent" icon="database">
    The file stores the same serialized entries every backend uses. Export from SQLite and import into MySQL, PostgreSQL, Redis, or YAML — in any direction.
  </Card>

  <Card title="Validated before writing" icon="shield-check">
    `.ppk` is a small binary format with a version number and checksum. On import the file is fully parsed and every kit test-decoded **before** anything is written.
  </Card>

  <Card title="Sandboxed to the plugin folder" icon="folder">
    Files are only ever read from and written to `plugins/PerPlayerKit/`. Names may contain letters, numbers, dots, dashes, and underscores.
  </Card>

  <Card title="One at a time" icon="lock">
    Only one export or import can run at a time.
  </Card>
</Columns>

<Warning>
  A corrupted, truncated, or malformed file is rejected as a whole rather than partially applied. Even so, only import `.ppk` files from people you trust — treat them like a downloaded plugin or world.
</Warning>

## Recipes

<Tabs>
  <Tab title="Hand a setup to another owner">
    ```bash
    /kitroom save
    /kitdata export kitroom my-kitroom
    /kitdata export publickits my-publickits
    ```

    Send them both files. They drop them in `plugins/PerPlayerKit/` and run `/kitdata import my-kitroom` and `/kitdata import my-publickits`. Public kit config entries are created for them automatically.
  </Tab>

  <Tab title="Seed a test server">
    ```bash
    /kitdata export all prod-snapshot
    ```

    Copy `prod-snapshot.ppk` to the test server's plugin folder and import it there. Storage backends do not need to match.
  </Tab>

  <Tab title="Off-site snapshot">
    ```bash
    /kitdata export all weekly-2026-08-21
    ```

    Unlike automatic [backups](/configuration/backups), this works on MySQL, PostgreSQL, and Redis too — one file you can copy anywhere.
  </Tab>
</Tabs>

## Compared With the Other Data Tools

| Tool                                                    | Moves                    | Works on                    | Use it to                                        |
| ------------------------------------------------------- | ------------------------ | --------------------------- | -------------------------------------------------- |
| `/kitdata`                                              | A file you carry         | All backends                | Move a setup to an unrelated server               |
| [`/perplayerkit migrate`](/guides/storage-migration)    | Backend → backend        | All backends                | Change storage type on the same server            |
| [Automatic backups](/configuration/backups)             | Timed local snapshots    | SQLite and YAML only        | Recover from corruption or a mistake              |
